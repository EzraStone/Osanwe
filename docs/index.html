Osanwë

An anonymity network for AI inference. Use frontier models without the provider being able to link the prompt to a person — and pool contributed hardware to serve open-weight models for those who would rather trust no one at all.

Design document Status: prototype implementation Revision 2

01Executive summary

The original idea contained two different systems fused into one sentence. Separating them is the single most valuable thing this document does, because one of the two is crowded and largely solved, and the other is genuinely open.

The starting premise was: a Tor-like P2P network where people contribute DGX Sparks to share compute, with traffic routed through multiple nodes, giving users anonymity with frontier models.

Frontier models are closed-weight. Nobody can run Claude or GPT‑5 on a donated DGX Spark. So in any frontier-model path, contributed hardware is not performing inference — it is forwarding bytes. That single fact splits the project cleanly in two, and the halves have almost nothing in common except a node network.

What a node doesForwards encrypted bytesActually executes model layers

Recommendation

Build System A first. It is the differentiated piece, it needs no GPUs to bootstrap, and it can ship a real product in weeks rather than quarters. System B reuses System A's node identity, reputation and payment rails, so this ordering forecloses nothing.

The second reframe is just as load-bearing: routing is the easy half of anonymity, and it is not the half that matters here. Onion routing hides your IP address. But the request still carries an API key bound to a credit card bound to your name. Ten hops do not help. The real problem is anonymous authorization, and it is solved with blind signatures, not with circuits.

02The premise, examined

2.1 What contributed hardware can and cannot do

A DGX Spark contributed to this network can do exactly one of two things:

  1. Forward packets toward a frontier provider. This requires ~0% of its compute. A Raspberry Pi does it equally well. The Spark is a $4,000 router.
  2. Run open-weight models, either alone or as one stage of a pipeline split across peers. This is real work — but the output is Llama or Qwen, not Claude.

There is no third option in which donated consumer hardware contributes compute to a frontier model. The weights are not public and never leave the provider's datacenter. Any pitch that implies otherwise is, on inspection, false, and will be recognized as false by exactly the technically literate audience this project needs.

2.2 What the relay actually buys the user

The threat to defend is: the provider links this prompt to this person. Identity leaks through five distinct channels, and they are not equally hard.

#Leak channelFixed by onion routing?What actually fixes it
1IP address / network locationYesAny relay. One hop suffices
2API key / account identityNoBlind-signed tokens + pooled access
3Payment instrumentNoUnlinkable issuance; Monero or cash-equivalent
4Prompt content & writing styleNoNothing. Unfixable at network layer
5Traffic timing correlationPartlyPadding, cover traffic, mixnet — all costly
The uncomfortable one

Channel 4 cannot be engineered away. A user who pastes their proprietary codebase, names their employer, or simply writes in a distinctive voice has deanonymized themselves regardless of how many hops the packet took. Stylometric attribution over long-form text is effective and well studied. This must be stated plainly in user-facing documentation, not buried. A privacy product that lets users believe they have protection they do not have is worse than no product.

2.3 The favourable asymmetry Tor does not have

Tor's exit node must handle plaintext because it speaks arbitrary protocols to arbitrary destinations. That is the origin of Tor's worst operational problem: exit operators see traffic, attract abuse complaints, and get raided.

Osanwë's destination set is small and known, and every member speaks TLS. If relays act as plain CONNECT tunnels, the client's TLS session terminates at api.anthropic.com and no node in the network ever observes a prompt. The exit node problem disappears.

But this is exactly where the argument bites back: an end-to-end TLS session must present a credential the provider accepts, and that credential is the identity (channel 2). Resolving that tension is the entire architecture in §6.

03Naming

The repository is Osanwe in ASCII contexts. The intended prose name is Osanwë.

The name is well chosen and is retained. In Tolkien's Ósanwe-kenta — "Enquiry into the Communication of Thought" — ósanwë is direct mind-to-mind transmission of thought. The essay's central doctrine is that a mind is open by nature but may close itself against intrusion, and that no power can rightfully force it open. That is this project's thesis almost verbatim: a prompt is thought in transit, and the network is the barrier.

Rendered osanwe in ASCII contexts — package names, domains, the repository — with Osanwë in prose. Components take their names from the same world:

04Threat model

Written first, deliberately. Every architectural decision below is downstream of this section, and any decision that cannot be traced back to it is decoration.

4.1 Assets

  • Prompt and completion content — often the most sensitive thing a user owns: code, medical questions, legal strategy, unpublished writing, security research.
  • The linkage between a user's real identity and their prompts. Distinct from content, and the primary asset this system protects.
  • The fact of use — that a given person uses AI at all, or at what volume.
  • Node operator safety — operators must not be exposed to liability for traffic they cannot read.

4.2 Adversaries

AdversaryCapabilityIn scope?
The providerSees every prompt in plaintext; wants to attribute it to an account, card, IPPrimary target
A relay operatorSees client IP, packet timing, volume. Malicious or merely curiousYes
A gateway operatorSees prompt content; wants to attribute it to a userYes
The user's ISP / employerSees the user's uplink; wants to know they use AIYes
Colluding relay + gatewayTogether reconstruct the full linkageExplicitly assumed not to occur
Global passive adversaryObserves the entire network; correlates by timingOut of scope — see §8
Adversary who compromises the clientEndpoint malware, keyloggerOut of scope

4.3 Security goals

  1. Unlinkability at the provider. The provider can serve the request but cannot tie it to a name, payment instrument, or IP.
  2. Content confidentiality from the network. No relay operator ever sees a prompt.
  3. Issuance–redemption unlinkability. The mint, which knows who paid, cannot correlate a purchase with any later request — even in collusion with the gateway.
  4. Verifiable gateway integrity. Where a gateway must see plaintext, the client can cryptographically verify what code will see it before sending.
  5. Operator plausible deniability. A relay operator can prove they were technically incapable of reading the traffic they carried.

4.4 Explicit non-goals

Osanwë does not, and will not, protect against
  • Self-deanonymization through prompt content or writing style (§2.2, channel 4).
  • A global passive adversary performing end-to-end timing correlation.
  • Relay and gateway colluding against a specific targeted user.
  • Compromise of the user's own device.
  • Evading the provider's safety systems. This is a non-goal by intent, not by limitation — see §11.

05Why this is not a Tor clone

Tor's design answers a harder and differently-shaped question than ours, and copying it would import cost without importing benefit.

PropertyTorOsanwëConsequence
Destination setThe entire internet, arbitrary protocolsA handful of known TLS APIsWe can pin certs and require TLS. No plaintext exit
Exit sees plaintextYes — Tor's core operational woundNo, in the BYOK pathRemoves abuse-complaint exposure for relays
AuthorizationNone — the web is openMandatory — APIs are paid and keyedThis is our hard problem; Tor never had it
Traffic shapeBursty page loadsLong-lived token streamsStreaming is far more fingerprintable
Latency toleranceSeconds acceptableTTFT is the productHop count is a product decision, not a security dial
Sybil defenceDirectory authorities, consensusSame idea — reuse it, don't reinventBorrow Tor's consensus design wholesale

The right ancestor is not Tor but Oblivious HTTP (RFC 9458) and the deployed systems built on it — Apple's iCloud Private Relay, Cloudflare's Oblivious DoH. Those systems solve precisely our shape of problem: a known destination, a mandatory credential, and a hard latency budget, split across two non-colluding parties.

06Architecture

Three parties, split so that no single one ever holds both halves of the user's identity. This is the OHTTP shape, extended with unlinkable payment and an attested gateway.

6.1 eregion — the token mint

The user pays by card, bank transfer, or Monero for N request-tokens. The mint issues them through a blind signature, so the tokens it later sees redeemed are cryptographically unlinkable to the purchase that produced them. The mint learns a billing identity and precisely nothing else — not a prompt, not a model choice, not a timestamp of use.

The mint is the one component that may be centrally operated and KYC-compliant without weakening the system, which is convenient: it is also the component that must handle money.

6.2 ranger — the relay

Sees the client's IP address and an encapsulated request body it cannot decrypt. Forwards it to a gateway. Cannot read content, cannot learn which provider or model was requested, cannot link two requests from the same user unless the user is careless about circuit reuse.

Because relays never touch plaintext, running one carries dramatically less legal exposure than running a Tor exit — a fact that should be central to operator recruitment.

6.3 mithlond — the exit gateway

Terminates the encapsulated request, verifies the token has not been spent, and calls the provider using a pooled account key. It sees prompt content but never learns which user sent it.

To keep "sees content" from meaning "the operator reads your prompts", the gateway runs inside an attested Trusted Execution Environment — Intel TDX for the CPU domain plus NVIDIA Confidential Computing where GPU work is involved. Composite CPU+GPU attestation lets bearer verify the exact gateway binary before transmitting anything. Measured overhead for confidential LLM inference is under roughly 7%, dominated by PCIe bus encryption rather than compute — an affordable price.

State the assumption loudly

Non-collusion is the security assumption. Mint, relay and gateway must be operated by distinct parties, ideally in distinct jurisdictions, with published ownership and divergent incentives. This is the same assumption Apple's Private Relay makes. It is honest and defensible — but only if it is stated in the user-facing documentation rather than hidden in an appendix. A privacy claim whose assumptions are concealed is a lie with extra steps.

07Protocol detail

7.1 Token issuance and redemption

Built on the Privacy Pass family — architecture in RFC 9576, the HTTP authentication scheme in RFC 9577, issuance protocols in RFC 9578, with RSA blind signatures per RFC 9474. These are deployed, reviewed standards; do not invent a bespoke scheme.

ISSUANCE                                        (bearer ↔ eregion)
  1. bearer:   t_i     ← random nonce, for i in 1..N
               m_i     ← RFC9474.PrepareRandomize(domain ‖ key-id ‖ t_i)
               b_i     ← RFC9474.Blind(PSS(m_i), r_i) r_i random blinding factor
  2. bearer  → eregion : payment, [b_1 … b_N]
  3. eregion → bearer  : [s_1 … s_N]  where s_i = Sign(sk_mint, b_i)
  4. bearer:   σ_i     ← RFC9474.Finalize(s_i, r_i)
               token_i = (m_i, σ_i)                  standard RSA-PSS signature

  The mint has seen b_i, never t_i. Given a redeemed (t_i, σ_i) it cannot
  determine which blinded value it signed. Anonymity set = all tokens issued
  under the same key epoch.

REDEMPTION                                      (bearer → ranger → mithlond)
  5. bearer:   ct      ← HPKE.Seal(pk_gateway, request ‖ token_i)
  6. bearer  → ranger  : ct, gateway_id           ranger sees IP, cannot open ct
  7. ranger  → mithlond: ct                        mithlond sees no client IP
  8. mithlond: open ct; Verify(pk_mint, t_i, σ_i); check t_i ∉ spent_set
               spent_set ← spent_set ∪ {t_i}        double-spend prevention
  9. mithlond → provider : request, using pooled API key
 10. response streams back along the same path, encrypted to bearer
Key epochs are an anonymity parameter

All tokens signed under one mint key form a single anonymity set. Rotating keys too often shrinks that set until tokens become individually identifying; rotating too rarely delays revocation of compromised keys. Publish the epoch schedule, make key material auditable through a transparency log, and treat "how many users share my epoch" as a number shown in the client.

7.2 Attestation flow

  1. bearer requests a quote from mithlond before first use
  2. mithlond returns composite evidence:
       - Intel TDX quote over the CPU TD measurement
       - NVIDIA CC attestation report for the GPU, chained to the TD
       - the HPKE public key, bound into the quote's report data
  3. bearer verifies:
       - signature chains to Intel / NVIDIA roots
       - measurement == published, reproducible build of mithlond
       - pk_gateway in report data == the key it will encrypt to
  4. only on success does bearer transmit

Binding pk_gateway into the attestation report data is what prevents a man-in-the-middle from presenting a valid quote for a genuine enclave while substituting its own encryption key. Reproducible builds are a hard requirement, not a nicety: an unverifiable measurement makes the whole attestation theatre.

7.3 Circuit and directory design

  • Directory (council). Signed node descriptors, consensus documents, bandwidth weighting — borrow Tor's design rather than inventing one. It is a solved problem with two decades of adversarial review.
  • Relay selection. Weight by measured bandwidth and latency, constrained so that relay and gateway never share an operator, an ASN, or a jurisdiction.
  • Circuit lifetime. Requests from one user over one circuit are linkable to each other by the relay. Rotate per conversation by default; expose a "new identity" control.
  • Cert pinning. The client pins provider certificates so a hostile gateway cannot transparently proxy in the BYOK path.

08How many hops

Three hops is Tor's answer to a different question. For a known TLS destination the calculus changes completely.

ConfigurationDefeatsFails againstLatency cost
1 relay + gateway (default)Provider linking prompt→IP; gateway learning identityRelay+gateway collusionOne extra RTT
2+ relaysAdditionally, a single hostile relay near the clientGlobal observerMeaningful; measure it
Mixnet (Nym-style)Global passive adversary—Seconds. Disqualifying
Do not promise a mixnet

Mixnets defeat a global passive adversary by deliberately adding latency: batching, reordering and cover traffic. They are designed for unlinkable one-shot messages, not for a session that streams tokens for thirty seconds. Routing interactive LLM traffic through one produces an unusable product. If a nation-state threat model is genuinely required, the honest answer is a different product — asynchronous, batch, store-and-forward — not a slower version of this one.

The empirical evidence on hop cost is encouraging: the processing overhead of extending a Tor circuit is small — roughly 3–4 ms of added latency per additional hop. Tor feels slow not because of its cryptography but because of circuitous paths, congestion and unweighted relay selection. A small, well-provisioned, latency-weighted relay set should perform far better than public Tor. This is a testable hypothesis and Phase 0 tests it.

Design decision: circuit length is a user-selectable policy defaulting to one relay, with measured latency published for each setting. Do not pick a number on vibes and do not let a security aesthetic silently tax every user.

09Latency budget

The product lives or dies on time to first token. Users forgive throughput; they do not forgive a cursor that sits still. Inter-token latency matters second, because a stream that stutters reads as broken even when total time is fine.

PathTTFT targetVerdict if met
Direct to providerbaseline (measure per region)control
1 relay + gateway< baseline + 150 msViable for interactive chat
2 relays + gateway< baseline + 400 msViable as a hardened opt-in
3-hop Tor-stylemeasure — expect several hundred ms to secondsBatch workloads only
MixnetsecondsReposition or abandon

Measurement methodology

  • Measure from at least three client regions against at least two provider regions.
  • Report p50, p95 and p99. A privacy tool with a good median and a terrible tail is a bad product; the tail is what users remember.
  • Separate connection setup (amortizable across a session) from per-request overhead (not amortizable). Only the latter belongs in the steady-state budget.
  • Measure inter-token latency distribution, not just TTFT.
  • Hold the prompt and model fixed; provider-side variance will otherwise swamp the signal.
Go / no-go

If the single-hop path lands within ~150 ms of baseline, Osanwë is a chat product. If it does not, it is an async and agentic-workload product — still valuable, but a different positioning, a different UI and a different go-to-market. Learn this in week one, from measurement, before any protocol code exists.

10Existential risk I — Terms of Service

Pooling API keys so that many users share one provider account is very likely a violation of provider terms: account sharing, misrepresentation of the account holder, and circumvention of rate-limiting and abuse controls. A pooled key can be revoked at any moment, which makes it a single point of failure for the entire network.

This is not a compliance footnote. It determines whether the company can exist. There are three coherent postures:

Decided — see ADR 0001

Ship BYOK as v1. It is honest, compliant, immediately useful, and it builds the relay network, the operator community and the latency data needed for everything else. Open the cooperative conversation with providers in parallel — they have a genuine reputational interest in users being able to prove privacy rather than trust it, and at least one major platform vendor has already shipped a relay of this exact shape. Treat the adversarial path as a research branch, never the roadmap.

11Existential risk II — abuse

An anonymous, unattributable frontier-model proxy is precisely the tool someone wants for generating CSAM, malware, targeted harassment or fraud at scale. If the project's answer is "we cannot tell, we are anonymous," then the network becomes the abuse vector, and it will be shut down — deservedly.

Abuse resistance must be designed in from the first commit. It is not a feature to add after the first incident, because after the first incident there is no project.

Written up — see the abuse policy

The controls below are specified in full in docs/abuse-policy.md, together with prohibited uses, an honest account of what each component can and cannot see, the deliberately excluded controls (no content logging, no backdoors, no client-side scanning), the in-enclave classification tradeoff, legal obligations for counsel, and incident response. Note that System B is the harder case: open weights on donated hardware have no upstream provider safety layer behind them at all.

The positioning, stated once and everywhere

Osanwë provides anonymity from identity linkage. It explicitly does not provide freedom from model safety policy. Those are different products; only one of them is defensible, and conflating them would poison the first. Every piece of marketing copy must hold this line.

12System B — erebor, the compute market

Deferred to Phase 4, and reshaped by two findings that undercut the intuitive design.

12.1 Splitting a model across peers is not a privacy mechanism

This is the finding that changes the design

Petals-style pipeline parallelism passes intermediate activations between peers. Recent prompt inversion research recovers the original input prompt from those activations at near-perfect fidelity. The reassuring intuition — "each node only sees a meaningless slice" — is false. Related work demonstrates the same reconstruction for images in distributed multimodal inference.

Consequently, privacy in erebor comes from per-node TEE attestation, exactly as in mithlond, and not from the topology. Proposed mitigations such as information-bottleneck privacy adapters — compressing activations through a low-dimensional subspace with bounded reconstruction error — are promising but unproven at production quality; track them, do not depend on them.

12.2 The DGX Spark's real shape

SpecValueImplication
Unified memory128 GB LPDDR5XHolds models a consumer GPU cannot
Memory bandwidth~273 GB/sThe binding constraint on generation
CPU20-core ARM Neoverse-V2Ample for orchestration and relay duty
Prompt processingCompute-bound — strongGood at long-context ingest
Token generationMemory-bound — weakThe user-visible weakness

Reported generation figures vary by runtime and quantization, but the shape is consistent: on the order of tens of tokens per second for a large MoE model in a 4-bit format, falling to low single digits for a 70B dense model at 8-bit. Published benchmarks put a 120B MoE around 38 tok/s and a 70B dense model at Q8 near 2–3 tok/s. Re-measure independently before publishing any number; single-stream review figures also understate achievable aggregate throughput under concurrency.

Position honestly

The Spark's contribution is capacity, not speed — it holds models that will not fit elsewhere. Combine that with WAN latency between peers and the honest niche for erebor is batch, asynchronous and agentic workloads: overnight document processing, bulk evaluation, long-running agent loops. It is not an interactive chat backend, and marketing it as one guarantees churn from disappointed users.

12.3 Additional unsolved problems

  • Verification of work. How do you know a node ran the model it claimed rather than a cheaper one? Redundant execution costs multiples; TEE attestation is the more practical answer.
  • Integrity under malicious nodes. A peer can return subtly wrong activations. Detection is an open research area.
  • Straggler sensitivity. Pipeline parallelism runs at the speed of the slowest participant; one residential uplink can stall a whole circuit.
  • Free-riding and Sybil resistance in whatever incentive model is chosen.

13Build phases

PHASE 0 Latency spike days · do this first

Before any protocol design: a throwaway single-hop TLS CONNECT proxy on a VPS in another region. Stream a real provider API call through it. Measure TTFT and inter-token latency against a direct call, per the methodology in §9.

The tooling for this is written and tested — see tools/README.md. It needs an API key and a VPS in another region, and takes about twenty minutes.

Exit criterion: a latency table committed to docs/phase0-results.md, and a written go/no-go on whether Osanwë is a chat product or a batch product. Every later phase depends on this answer, so nothing else starts until it exists.

PHASE 1 Documentation days

This document, split and committed as docs/architecture.html, docs/product/privacy-boundaries.md and docs/abuse-policy.md. The privacy boundaries state explicitly what is not defended — especially stylometric self-deanonymization. Rename the repository to osanwe.

Exit criterion: a reader can state, unprompted, what Osanwë does not protect against.

PHASE 2 bearer + ranger, BYOK weeks · v1 product

Client and relay. The user's own API key, end-to-end TLS to the provider, no node able to see plaintext. Signed node descriptors and a minimal council directory modelled on Tor's consensus. ToS-clean, shippable, genuinely useful.

Exit criterion: a third party runs a ranger the team does not control, and a packet capture at that relay demonstrably contains no plaintext prompt.

PHASE 3 eregion + mithlond months

Blind-signed tokens, pooled access, TEE gateway with client-side attestation verification and reproducible builds. This is where "the provider cannot identify you" becomes literally true — and where the §10 ToS decision must already have been made.

Exit criterion: an external cryptographic review of the issuance protocol, plus a demonstration that the client refuses a gateway whose measurement does not match the published build.

PHASE 4 erebor months

Open-weight models on contributed hardware, TEE-attested nodes, reusing Phase 2 node identity and Phase 3 payment rails. Positioned for batch and agentic workloads per §12.

Exit criterion: a job runs across three independently-operated nodes with verified attestation and a cost per token beating centralized inference for the target workload.

PHASE 5 Traffic-analysis hardening ongoing

Padding, cover traffic, multi-hop circuits, pluggable-transport-style obfuscation — all as opt-in modes with honestly published latency costs.

Exit criterion: a documented adversary exercise showing measured resistance to a stated traffic-analysis attack, with its latency price stated alongside.

15Open questions

These were raised during design and remain unanswered. Each materially changes the plan.

  1. Trust model for the node network. Volunteer and reputation-based, Tor-style? Crypto-incentivized DePIN? Or federated paid operators with contractual non-collusion? This document assumes federated paid operators, which is the fastest route to a credible non-collusion claim but caps organic growth. A token model solves supply-side growth and imports securities questions.
  2. Is the global-passive-adversary threat model actually required? Assumed no. If yes, §8 forces a different, asynchronous product.
  3. Which posture on §10? Resolved: BYOK first, cooperative in parallel, adversarial never — recorded in ADR 0001.
  4. Jurisdiction. Where do the mint and gateway incorporate? This drives the credibility of the non-collusion claim and the exposure of the entity holding money.
  5. Does the mint's KYC obligation leak more than assumed? A payments processor that knows purchase volume and timing may narrow the anonymity set more than the cryptography suggests.
